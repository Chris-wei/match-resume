# 网页后台 + 反馈数据留存 设计

日期：2026-11-05
状态：待确认（已过实现者审阅）

## 1. 为什么要做

产品上线后要持续优化诊断质量（提示词、模型、打分）。现在的数据存储撑不起这件事：

- 用户反馈存在 `data/db.json` 里，**没有任何查看界面**，只能手敲命令读 JSON
- 报告 30 天过期删除、用户也可随时删除，反馈却保留 90 天 → 时间一长反馈就对不上报告
- 反馈只有整份报告"准不准"，不知道**哪一条**判错了
- 报告没记录当时的模型和提示词版本，无法对比"改动前后用户反馈有没有变好"

目标：让开发者（唯一的管理员）能在网页上看到用户反馈，点进去看对应报告的完整诊断信息，并且有反馈的报告不会消失。

配套的离线评测（`npm run eval`，模拟样本）已经有了；这次补的是**真实用户**这一侧的数据。

## 2. 目标 / 非目标 / 反目标

**目标**
1. 网页后台：反馈列表 → 点进去看报告详情（含用户看不到的诊断信息）
2. 有反馈的报告长期保留，不随 30 天过期删除
3. 小程序报告页每条判定可以标记"这条判错了"，后台能看到具体是哪几条
4. 每份报告记录生成时的模型与提示词版本

**非目标（这次不做）**
- 多管理员 / 角色权限
- 在后台修改数据、回复用户
- 把用户反馈一键转成评测样本（以后可能做）
- 图表、导出、按版本统计对比（列表能按版本筛就够了，见 §5.2）
- 没有反馈的报告的浏览入口
- 把存储从 JSON 文件迁到数据库

**反目标（做到了也算失败）**
- 后台在没登录的情况下能看到任何数据
- 用户删除报告后，后台仍能看到他的简历原文或能把报告关联回这个用户
- 保留报告却没在隐私政策里写明、没让用户知情

## 3. 数据留存规则（已和产品负责人确认）

### 3.1 什么算"有反馈"

一份报告只要满足任一条件就是"有反馈的报告"：
- 用户提交过整份报告的反馈（现有表单：q1 准不准 / q2 最有用模块 / 留言）
- 用户在任意一条判定上点过"这条判错了"（§4 新增）

### 3.2 保留规则

| 情况 | 处理 |
|---|---|
| 没有反馈的报告 | 不变：30 天过期删除，用户删除即彻底删除 |
| 有反馈的报告，**过期** | **不删除**，长期保留。用户侧照旧表现为"已过期"（看不到、列表里不出现），只有后台能看 |
| 有反馈的报告，**用户主动删除** | **脱敏留存**：删掉一切来自简历的内容和与用户的关联，保留不含个人信息的部分（见 3.3）。用户侧表现与现在一样（报告消失） |
| 反馈记录本身 | 跟随报告长期保留（不再按 90 天清理） |

**过期保留时断开与用户的关联**（实现者决定，见 §7.1）：有反馈的报告过期时，清空 `owner`、`inputHash`（报告与反馈记录都清），保留简历行和其余内容。过期后用户本来就看不到、也删不了这份报告，留着身份关联没有用处，只增加风险；后台优化也不需要知道是谁。

### 3.3 用户删除时的脱敏留存

**删除**：
- `spans`（脱敏后的简历行）
- 每条判定的 `quote`、`quoteId`（简历引用）
- `rewrites`（改写建议里含简历原句）
- `owner`、`inputHash`（报告与用户的关联）；对应反馈记录的 `owner` 一并清掉
- `usage` 里引用这份报告的记录（复制计数的 `ref = reportId#idx`）把 `ref` 清掉，计数本身保留（不影响当日限次）
- 反馈留言 `comment` 保留（用户主动写给我们的，且入库前已脱敏，见 §4.3）

**保留**：`requirements`（来自 JD）、每条判定的 `verdict` / `reason` / `flags` / `yearsHint`、`score`、`conclusion`、诊断元数据（§5.3）、反馈（q1/q2/留言/判错条目）。

**打标**：`deletedByUser: true`、`deletedAt`。后台详情页显示"用户已删除，简历内容已清除"。

> 已知风险（已接受）：判定理由 `reason` 是模型写的，常会转述简历片段（如"S4 写明'负责江浙沪制造业客户开拓'"）。保留理由是这个折中的一部分；简历已无姓名联系方式、且与用户身份断开关联，风险可接受。隐私政策需如实写"保留分析结论和判定理由"。

### 3.4 用户知情

- **隐私政策**（`miniprogram/pages/legal/legal.wxml` §4、§5，生效日期更新）补充：提交反馈或标记判错的报告会被保留用于改进分析质量，不受 30 天限制；删除这类报告时会清除简历内容，仅保留分析结论、判定理由和反馈。
- **整份反馈表单**：提交按钮上方加一行小字："提交后这份报告将被保留，用于改进分析质量（删除时会清除简历内容）"。
- **逐条判错按钮**：每台设备第一次点击时弹窗确认（同样的说明 + "确定标记 / 取消"），确认后本地记住，以后直接生效。

## 4. 小程序：逐条"这条判错了"

### 4.1 交互

- 报告页「逐条判定」每一条的右下角加一个轻量按钮"判错了？"
- 点击 → 标记该条（按钮变为"✓ 已标记判错"，可再点取消）
- 标记即时提交服务端；失败时恢复按钮状态并 toast 提示
- 不要求用户说明原因（降低门槛）；需要说明的可以走整份反馈的留言
- 重新打开报告时，已标记的条目保持标记状态（由服务端返回）

### 4.2 接口

`POST /api/report/:id/flag`，body `{ reqId, wrong: true|false }`
- 只能标记自己的、未过期的报告；`reqId` 必须是该报告里存在的要求
- 幂等：重复标记同一条不重复记录
- 返回 `{ ok: true, wrongItems: [...] }`
- 风控：每人每天标记操作上限（建议 100 次，防刷），超限返回 `RATE_LIMITED`。这条限流计数**不记 reportId**（只记 owner、时间），避免 usage 里留下报告与用户的关联

`GET /api/report/:id` 与分析完成时返回的报告里，增加 `wrongItems: [reqId...]`（当前用户对这份报告的标记）。

### 4.3 存储

逐条判错和整份反馈存在同一条反馈记录里（每个用户 × 每份报告一条，沿用 `upsertFeedback` 的唯一性）：

```
feedback: {
  owner, reportId,
  q1, q2, comment,            // 整份反馈（可能为空：用户只标了判错没填表单）
  wrongItems: [{ reqId, at }],// 逐条判错
  createdAt, updatedAt
}
```

- 现有"整份反馈"提交时要**合并**而不是覆盖整条记录（否则会抹掉 wrongItems）
- 留言 `comment` 入库前过一遍服务端 `redact()`（去联系方式），现在没做
- 第一次产生反馈时给报告打 `retained: true`（§3.2 依据它判断是否保留）。取消所有判错标记且没有整份反馈时**不**取消 retained（简单起见，保留只增不减）

## 5. 网页后台

### 5.1 访问与安全

- 地址：同一个 Node 服务下的 `/admin`（页面）和 `/admin/api/*`（数据接口），不新增进程和端口
- 开关：环境变量 `ADMIN_PASSWORD`。**未设置则后台完全关闭**（`/admin*` 一律 404）
- 登录：密码输入 → 服务端常量时间比较 → 下发 HttpOnly + SameSite=Strict 的会话 cookie（HMAC 签名，复用 `auth.js` 的密钥机制），有效期 12 小时；部署在 HTTPS 后时加 Secure
- 登录防爆破：同一 IP 10 分钟内失败 5 次即锁定 10 分钟
- 所有 `/admin/api/*` 都校验会话；后台接口与小程序接口的 token 互不通用
- 页面响应头加 `Cache-Control: no-store`

### 5.2 反馈列表（首页）

- 顶部汇总：近 7 天 / 全部 的反馈数；"准 / 部分准 / 不准"占比；被标记判错的条目总数
- **一行 = 一份报告**（每份报告只有一个 owner，所以每份报告至多一条反馈记录）
- 列表按最近更新时间倒序，每行：时间、准不准、最有用模块、判错条数、留言（截断）、报告总分、一句话结论、报告状态（正常 / 已过期 / 用户已删除 / 报告已不存在——上线前就过期删掉的旧报告，只剩反馈）、生成时的判定模型 + 提示词版本
- 筛选：准不准（全部 / 准 / 部分准 / 不准 / 未填）、只看有判错标记、只看有留言、版本
- "版本"= 判定模型 + `jd-split.txt` 与 `judge.txt` 的哈希组合成的一个标签（这两个文件决定诊断结果；`rewrite.txt` 只影响改写建议，不参与）。下拉框列出数据里出现过的所有版本标签
- 分页（每页 50 条）

### 5.3 报告详情

与用户看到的报告同样的内容，再加用户看不到的诊断信息：

- **反馈区（置顶）**：q1 / q2 / 留言；被标记判错的条目在下方逐条列表里高亮
- **总分、一句话结论、雷达五维数值**（雷达可用数字表格代替画图）
- **逐条判定表**：要求原文、JD 引用、类别/权重/年限、判定、理由、简历引用（已删除报告无此列）、flags（`evidence_rejected` / `downgraded_no_evidence` / `fuzzy_quote` / `judge_failed` 等）、用户是否标记判错
- **诊断元数据**：拆解模型、判定模型、各提示词版本、是否 mock、JD 拆解是否命中缓存、拆解被拒条数、判定失败条数、耗时、创建时间
- **简历**：脱敏后的简历行（S1..Sn），判定里引用到的行可以点击定位（已删除报告显示"简历内容已清除"）
- **改写建议**（已删除报告无）

### 5.4 报告新增字段（生成时写入）

```
meta: {
  model, judgeModel,            // 生成时的模型
  prompts: { 'jd-split.txt': 'xxxxxxxx', 'judge.txt': ..., 'rewrite.txt': ... },  // 各提示词内容短哈希
  mock
}
retained: false                 // 有反馈后置 true
```

提示词短哈希的算法与 `scripts/eval.js` 的 `promptVersions()` 一致：对 `server/prompts/` 下**所有文件**各算 sha256 前 8 位，得到 `{文件名: 哈希}`。**后台显示的版本号要能和评测结果文件里的对上**，所以两边应共用同一个函数（抽到 server 侧，eval.js 改为引用它）。启动时算一次。

存量报告没有 `meta`，后台显示"未记录"。

### 5.5 上线迁移（必须在启动清理 `db.prune()` 之前执行）

部署新代码后第一次启动，`prune` 会按新规则清理；在它之前先跑一次幂等迁移，否则已有反馈的报告会被当作"无反馈"删掉、无法恢复：
1. 有反馈记录的报告补 `retained: true`
2. 反馈记录补 `updatedAt`（取 `createdAt`）、`wrongItems: []`
3. 旧留言补跑 `redact()`

迁移逻辑写成 db 层的函数，启动时在 `prune` 前调用，可重复执行无副作用。

## 6. 约束

- 服务端保持零依赖（只有 pdfjs-dist）；后台页面不引入构建工具，单个 HTML + 原生 JS + 内联 CSS，由 Node 直接返回
- 存储仍是 `data/db.json`；长期保留会让文件持续变大，当前规模可接受，记录为已知问题
- 小程序端改动只限报告页和隐私政策页
- 所有新接口沿用现有错误约定（HTTP 200 + `{ok:false, code, message}`；后台未登录返回 401）
